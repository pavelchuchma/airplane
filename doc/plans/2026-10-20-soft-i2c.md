# Bit-banged I2C for the sensor bus

**Superseded** 2026-10-21: the bus moved to the ESP-IDF 5 master driver
(`doc/plans/2026-10-20-arduino3-native-i2c.md`, phase 2); this
implementation lives on in history (`git show e65f783`).

Status: **implemented** 2026-10-20. Bench (USB, `2026-10-20_181432`, 33 s):
all sensors present, gyro bias in 1.0 s, zero `I2C ...` report lines (no
error, no stretch ≥ 50 µs, no read ≥ 10 ms), no freeze after the
calibration; the boot cleared a bus left stuck by the flash reset.
Battery (`2026-10-20_181656`, `204503`): no 1 s stall any more; the pitot's
remaining address NACKs cost one sample each. One slave-holds-SDA episode
in `181656` took the 2 s whole-bus rescue (two 2-3 s freezes), so every
transaction now checks both lines and clears the bus at once
(`i2cbus::lastCleared()`, `N bus freed` in the report); `204503` then had
no freeze at all. The glitches turned out to be a cold ground joint
(resoldered, clean since). Cleanup afterwards: the per-error timing lines,
the `slow I2C` line and the `-DAIR_NO_BATTERY` switch were removed, and the
stretch report threshold went from 50 µs to 1 ms (WiFi interrupts preempting
the wait show up as 70-530 µs "stretches" on a clean bus). Findings:
`doc/todo/002`.

## Why

The ~1 s sensor-task stalls of `doc/todo/002` are, every single one, an
MS4525DO read that takes 1006–1008 ms and then *succeeds*
(`2026-10-20_175900` and `180823`, on battery; video chain ruled out).
Exactly 1 s regardless of `Wire.setTimeOut(20)` comes from somewhere in
the Arduino/IDF driver stack (first blamed on the IDF alive interval -
wrong, see `doc/todo/002`). The driver cannot tell us what the bus did,
and it cannot be made to give up sooner.

`sensorTask` already owns the bus exclusively, and the traffic is ~30 B per
20 ms tick, so the ESP32 can drive the two pins itself. That gives:

1. **Bounded transactions.** Every wait has its own timeout (clock
   stretching 2 ms), so a misbehaving pitot costs at most one sample, never
   a second of horizon.
2. **A view of the bus.** Each transaction reports *how* it failed: bus busy
   before START (SDA/SCL held low), address NACK, data NACK, SCL stretched
   past the timeout, or SDA read low while we released it (someone else
   driving it — a glitch). Plus the longest clock stretch seen. These are
   exactly the facts that separate the remaining causes:
   - stretch/SDA-stuck/NACK bursts on the pitot only → the sensor
     misbehaves on battery (5 V buck supply, I2C levels) → hardware;
   - a clean bus and no stalls → it was the IDF driver → fixed.

## Design

- `src/air/i2cbus.{h,cpp}`: single-master bit-bang on GPIO21/22, pins as
  open-drain in/out with the internal pull-ups (as the Wire driver had),
  ~90 kHz (5 µs half periods, `delayMicroseconds`). API:
  `begin()`, `clear()` (the SCL-clocking rescue, moved from `main.cpp`),
  `writeRegs(addr, reg, data, n)`, `readRegs(addr, reg, buf, n)`
  (repeated START), `read(addr, buf, n)` (plain read, the MS4525DO). Each
  returns a `Status`; `lastMaxStretchUs()` gives the longest stretch of the
  last transaction. On any error a STOP is attempted, so the next
  transaction starts from an idle bus when possible.
- Drivers (`bmp280.cpp`, `ms4525do.cpp`, the MPU code in `main.cpp`) switch
  from `Wire` to `i2cbus`; Wire is no longer linked into the bus path.
- Diagnostics in `main.cpp`: per-sensor counters of each status, the max
  stretch and the max transaction time, reported once per second as one
  `diag` line per sensor *only when something happened* (any error, a
  stretch ≥ 50 µs, or a transaction ≥ 10 ms), e.g.
  `I2C MS4525DO 1s: 50 ok, 2 stretch-timeout, max stretch 2000 us, max 2.4 ms`.
  The old `slow I2C` line stays, threshold lowered to 10 ms.
- Interrupts stay enabled: WiFi on core 0 can preempt mid-bit, which only
  lengthens a clock phase (I2C is static). CPU cost ~3 ms busy-wait per
  20 ms tick on core 0.

## Verification

- Bench on USB: all sensors present, zero error lines over minutes.
- Battery session (the failing case): count freezes and read the new
  `I2C ...` lines in the `.air.log`.
